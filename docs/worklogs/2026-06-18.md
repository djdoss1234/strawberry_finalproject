## 오늘 확인한 핵심 문제

### 1. SW 성공 방식과 NW 실험 방식이 달랐다

SW 단일 딸기 성공 기준 로그는 `e0509_gripper_description`의 다음 runtime에 남아 있다.

```text
logs/runtime/2026-06-09/curobo_planner_node_20260609T160052-da5edd5a.jsonl
```

SW에서는 다음 구조로 동작했다.

```text
cuRobo pre-approach
 -> Doosan TOOL +Z MoveLine 20mm
 -> Doosan TOOL +Z extra advance 65mm
 -> close
 -> TOOL -Z retreat
```

반면 오늘 NW measured-TCP 실험은 다음 구조였다.

```text
cuRobo pre-approach
 -> measured TCP 기준 final approach를 cuRobo로 깊게 계획
 -> 실패 시 얕은 cuRobo fallback
 -> 필요 시 TOOL MoveLine fallback
```

즉, `SW에서는 됐는데 NW에서는 왜 안 되냐`의 직접 원인은 단순 좌표 문제가 아니라 motion policy 차이다. NW는 SW처럼 마지막 깊은 진입을 Doosan TOOL MoveLine으로만 처리한 것이 아니라, measured TCP 기준으로 cuRobo가 더 깊은 final approach를 풀어야 하는 구조였다.

### 2. NW에서 딸기까지 충분히 접근하지 못함

최근 실기 로그 예시:

```text
e0509_gripper_description/logs/runtime/2026-06-18/curobo_planner_node_20260618T145519-fe017af0.jsonl
```

관찰:

- target 예시: `(-238, 672, 819)mm`
- measured TCP direct final approach 사용
- cuRobo final approach 결과:
  - `150mm` IK_FAIL
  - `130mm` IK_FAIL
  - `110mm` IK_FAIL
  - `90mm` Plan OK
- 이후 남은 `60mm`를 SW 방식처럼 `TOOL +Z MoveLine`으로 보강하려 했으나, Doosan MoveLine이 success처럼 빠르게 반환하고 실제 joint 변화는 거의 없었다.

결론:

```text
물리적으로 절대 도달 불가능한 거리라기보다,
현재 선택된 measured-TCP 자세에서 cuRobo deep final approach가 막히고,
MoveLine fallback도 실제 이동 없이 success를 반환하는 것이 핵심 병목이다.
```

### 3. 속도 30% 증속이 실제 요청값에 반영되지 않았음

`SPLINE_TIME_SCALE`만 줄어 있었고, 실제 `MoveSplineJoint` 요청 velocity/acceleration은 여전히 하드코딩된 값이었다.

수정 후 기준:

```text
SPLINE_VEL_DEG_S  = 47.0
SPLINE_ACC_DEG_S2 = 70.0
SPLINE_TIME_SCALE = 0.87
SPLINE_MIN_TIME   = 0.58
```

다음 실기 로그에서 `velocity_deg_s=[47.0, ...]`가 찍히는지 확인한다.

### 4. NW/SW subcell을 먼저 스캔하던 이유와 원복

NW occlusion 실험 중 위쪽 잎/꼭지 후보를 먼저 잡는 문제를 피하려고 한때 scan order를 `sw -> se -> nw -> ne`로 바꿨다. 그러나 원인 분석에는 물리 scan 순서 변경이 방해가 되므로 다시 canonical visual order로 복구했다.

현재 scan order:

```text
nw -> ne -> sw -> se
```

단, candidate sorting/grouping 쪽에는 lower stem-level 후보를 우선하려는 변경이 남아 있다. 이는 `max_total_picks=1` 조건에서 높은 잎/꼭지 후보를 먼저 소비하는 문제를 줄이기 위한 것이다.
